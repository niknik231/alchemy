# Алхимия — правила проекта

## Источник и хостинг

- Исходники игры находятся в `src/`: шаблон разметки `src/index.html`, стили `src/styles.css`, данные `src/data/*.js`, логика `src/game/*.js`. Все правки игры вносить только туда.
- Корневой `index.html` — собранный результат; GitHub Pages отдаёт именно его. Вручную его не редактировать: он перезаписывается командой `node tools/build.mjs`.
- Публикация выполняется только через GitHub Pages:
  - репозиторий: `https://github.com/niknik231/alchemy`;
  - игра: `https://niknik231.github.io/alchemy/`;
  - ветка публикации: `main`, каталог: `/ (root)`.
- Интеграцию OpenAI Sites не использовать и версию на `chatgpt.site` не обновлять. Существующие `.openai/hosting.json`, `app/` и `public/game.html` считать устаревшими следами прежнего способа публикации, а не рабочим контуром размещения.
- Любые правки игры по умолчанию выполнять только локально. Не загружать их на GitHub без отдельной явной команды пользователя на публикацию.
- Команда пользователя вида «опубликуй», «обнови GitHub» или «выложи изменения» является окончательным разрешением обновить публикуемый набор файлов на GitHub. После такой команды не запрашивать повторное подтверждение публикации.

## Публикация через Git

- Локальная ветка `main` и `origin/main` имеют несвязанную историю. Не пытаться сливать их, перебазировать локальную ветку на удалённую или делать принудительный push.
- Публикуемый набор файлов: собранный `index.html`, каталог `src/`, `tools/build.mjs`, `tools/validate-game-data.mjs`, `AGENTS.md` и `CODEMAP.md`. Других файлов в `origin/main` быть не должно.
- Для публикации сначала выполнить `git fetch origin main`, убедиться, что `node tools/build.mjs --check` и валидатор проходят, затем создать временный detached worktree от `origin/main`, синхронизировать в нём публикуемый набор (включая удаление файлов, исчезнувших из `src/`), проверить diff и закоммитить публикацию там.
- Публиковать командой вида `git push origin HEAD:main`. После успешной проверки удалить временный worktree и выполнить `git worktree prune`, если осталась служебная запись.
- Не добавлять в публикационный коммит `public/game.html`, превью-картинки, `app/`, `.openai/`, файлы Next.js и любые другие локальные или служебные файлы.
- Доступ к GitHub сохранён в системном менеджере учётных данных. Для обычных `fetch` и `push` не открывать браузер авторизации и не просить пользователя войти повторно; если сеть ограничена песочницей, запросить только разрешение на сетевую команду.

## Общение с пользователем

- Сохранять элементы, рецепты и иконки сюрпризом: не выводить их списки или содержимое в чат.
- После массовых изменений сообщать только статистику: сколько элементов, рецептов, категорий, иконок и правил изменено.
- Конкретную иконку или элемент можно обсуждать только когда пользователь прямо просит об этом.

## Устройство игры

- Для игрока игра остаётся автономным HTML-файлом: сборка встраивает CSS, JavaScript и SVG-иконки в `index.html`, внешних зависимостей нет.
- Порядок JS-файлов задаётся списком `SCRIPTS` в `tools/build.mjs`. Файлы склеиваются в один `<script>` и делят общую область видимости, поэтому `import`/`export` не используются. Новый файл добавлять в этот список с учётом зависимостей.
- Не ломать сохранение прогресса в `localStorage` и не сбрасывать открытия пользователя без прямой просьбы.
- Справочник показывает заголовок каждой категории один раз; не дублировать название категории возле каждого элемента.
- В справочнике есть два режима: обычный категорийный список и список только неоткрытых элементов без показа рецептов. Неоткрытые элементы сортируются без визуальных разделителей: сначала результаты с двумя открытыми компонентами рецепта, затем с одним, затем с нулём; внутри одинаковой группы — по названию.
- Подсказки должны предлагать только ещё не открытые элементы. После открытия одного из предложенных элементов остальные предложения сохраняются, а освободившееся место заполняется новым доступным вариантом.
- Карточка элемента в панели показывает одним числом количество ещё не открытых рецептов с этим элементом. Для конечного элемента или при нулевом остатке индикатор не отображается.
- Такой же индикатор показывается в правом верхнем углу карточки на рабочем поле и строки открытого элемента в справочнике. Во всех трёх представлениях используется одна функция расчёта, чтобы числа не расходились.
- Нажатие кнопки `+` у элемента в справочнике добавляет его на рабочее поле, но не закрывает справочник и не сбрасывает поиск, режим или прокрутку.
- В подсказке рецептов открытого элемента показывать компоненты только для фактически открытых рецептов. Неоткрытый рецепт отображать как `❓ + ❓`, даже если сам результат уже был получен другим способом.
- Если игрок соединяет компоненты неизвестного альтернативного рецепта уже открытого результата, считать рецепт открытым, сохранить его и показать уведомление, не создавая дубликат результата.
- Чёрная дыра удаляет перетащенный на неё элемент только с рабочей области.

## Описания-намеки

- Описания предназначены для режима справочника «Неоткрытые» и показываются под названием элемента.
- Формулировка должна помогать догадаться о процессе, среде, свойствах или назначении результата, но не называть оба компонента напрямую и не превращаться в готовый рецепт.
- Сейчас это пилот: `ELEMENT_CLUES` содержит описания только для всех элементов на русскую букву «А». Не распространять описания на остальные элементы до отдельной команды пользователя после проверки стиля.
- При расширении проверять, что описание есть у каждого элемента выбранной буквы или группы и отсутствует у элементов вне согласованного охвата.

## Иконки

- Иконка должна передавать смысл элемента через узнаваемый предмет, форму или сцену, а не через условный круг подходящего цвета.
- Основной визуальный стиль — как у полноразмерных эмодзи: самостоятельный цветной объект на прозрачном фоне, без круглой подложки. Ориентир по подаче — иконка волка.
- Если иконка неоднозначна, перерисовывать весь образ целиком. Не добавлять маленькие поясняющие значки в углу: в мобильном размере они не читаются.
- Выбирать один главный, буквально узнаваемый образ элемента. Не заменять смысл косвенной ассоциацией, технологическим оборудованием или случайной сценой.
- Материалы изображать их характерной фактурой и формой: глыбой, слитком, листом, волокном, мешком, балкой и другими узнаваемыми образами.
- Похожие элементы должны визуально различаться по силуэту и композиции, а не только по оттенку. Особенно проверять пары вроде природного объекта и продукта его обработки.
- Не использовать символ готового изделия для исходного материала, если это меняет смысл элемента.
- Иконка должна оставаться читаемой в уменьшенной мобильной карточке и не зависеть от мелкого текста.
- Перед массовой отрисовкой неоднозначных образов сначала согласовывать в чате, что именно будет изображено. После согласования делать пробные варианты и показывать их пользователю до замены всего набора.
- Для предметов и явлений предпочитать буквальное изображение: мельница должна выглядеть как мельница, водопад — как поток с горного уступа, гном — как гном в характерной шапке, дворец — как богатое парадное здание.
- Не добавлять лишние объекты, которые меняют смысл: например, для бетона не нужен подъёмный кран, для дюны — кактус, для железа — форма магнита.
- Содержимое пищевой иконки должно быть очевидно по цвету и форме: например, в чашке йогурта должна читаться белая кисломолочная масса.

## Логичность рецептов

- Результат сочетания должен быть объясним обычной причинно-следственной, природной, технологической, бытовой или культурной связью. Хороший рецепт можно кратко объяснить одной фразой без натяжки.
- Оба исходных элемента должны существенно участвовать в смысле результата. Не создавать рецепт только из-за похожего цвета, иконки, звучания названия или случайной ассоциации.
- Сочетание считается неупорядоченным: `A + B` и `B + A` — один рецепт. Не создавать дубликаты одной пары.
- Один рецепт даёт один однозначный результат. Альтернативные способы получения уже существующего элемента добавлять только намеренно и после проверки механики подсказок и счётчиков.
- Каждый новый небазовый элемент должен быть достижим из базовых элементов через конечную цепочку уже достижимых рецептов. Не создавать недостижимые элементы и цепочки, которые зависят сами от себя.
- Не использовать результат в качестве одного из его же обязательных исходных элементов, если это единственный путь открытия результата.
- Сложность цепочки должна соответствовать смыслу результата: простые природные и бытовые сущности появляются раньше, сложные технологии, общественные, космические и фантастические понятия — позже.
- Не перегружать один универсальный элемент десятками случайных сочетаний. Участие элементов в рецептах должно быть достаточно равномерным и содержательно оправданным.
- Конечными делать только элементы, для которых отсутствие дальнейших рецептов является осознанным решением. Не создавать большое количество случайных тупиков.
- Перед добавлением набора рецептов проверять: уникальность пар, существование всех идентификаторов, достижимость каждого результата, отсутствие случайных циклов и соответствие счётчиков фактическому числу рецептов.

## Логичность категорий

- Категория описывает природу или назначение самого элемента, а не сложность его получения, используемые ингредиенты, визуальный вид иконки или сюжетный «уровень».
- Использовать понятные русские названия категорий с чётко различимым смыслом. Не создавать две категории с почти одинаковыми границами.
- Каждый элемент относится к одной основной категории. При неоднозначности выбирать наиболее привычное повседневное значение элемента.
- Материалы, природные объекты, живые существа, явления, технологии, общественные и фантастические понятия не смешивать без содержательной причины.
- Размер категорий не требуется искусственно выравнивать, но одиночную категорию создавать только при устойчивой необходимости и перспективе расширения.
- При изменении категории обновлять её состав и счётчики во всех представлениях, сохраняя единственный заголовок категории в справочнике.
- Перед массовой перекатегоризацией отдельно проверять пограничные элементы и устранять очевидные смысловые ошибки.

## Обратная совместимость сохранений

- Идентификатор существующего элемента является постоянным ключом сохранения. Не менять его при переименовании элемента, замене иконки, переносе в другую категорию или изменении рецепта.
- Не переиспользовать идентификатор удалённого элемента для нового элемента с другим смыслом.
- Сохранять существующий ключ `localStorage`: `alchemy.discovered`. Добавление новых элементов не должно менять формат уже записанного массива идентификаторов.
- Фактически открытые пары рецептов хранятся отдельно в `alchemy.discoveredRecipes` как массив канонических неупорядоченных ключей пар.
- При первом запуске версии с учётом отдельных рецептов старое сохранение мигрируется без сброса элементов: для каждого уже открытого результата известным считается только первый доступный рецепт, а альтернативы остаются скрытыми до фактического соединения.
- Не определять известность рецепта только по открытости результата: один результат может иметь несколько рецептов, и каждый из них открывается отдельно.
- При загрузке старого сохранения сохранять все известные открытые идентификаторы, удалять дубликаты, безопасно игнорировать неизвестные значения и гарантированно добавлять базовые элементы.
- Новые элементы после обновления остаются неоткрытыми; ранее открытые элементы и прогресс пользователя не сбрасываются.
- Изменение или удаление рецепта не должно закрывать уже открытый результат в существующем сохранении.
- Если изменение идентификатора неизбежно, добавлять явную версионированную и идемпотентную миграцию `старый ID → новый ID`. До миграции сохранять резервную копию исходного значения, не перезаписывая уже существующую копию.
- При изменении структуры сохранения вводить отдельную версию схемы. Каждая миграция должна корректно выполняться один раз и не повреждать данные при повторном запуске.
- Никогда не использовать `localStorage.clear()`. Удалять игровые сохранения только по прямой команде пользователя и только по относящимся к игре ключам.
- При пользовательском сбросе прогресса удалять `alchemy.discovered` и `alchemy.discoveredRecipes`, но не стирать несвязанные ключи браузера.
- Перед выпуском обновления проверять минимум три случая: частично открытая старая игра, полностью открытая прежняя версия и повреждённое сохранение с неизвестными или повторяющимися идентификаторами.

## Адаптивность

- Каждое изменение интерфейса и механики по умолчанию предназначено одновременно для мобильной и настольной версий. Ограничивать изменение одним режимом только по прямой просьбе пользователя.
- Мобильный режим начинается при ширине до `640px`; изменения мобильной компоновки не должны без необходимости менять настольную версию.
- В мобильной шапке кнопки показываются только иконками, но сохраняют доступные названия через `aria-label` и `title`.
- В обеих версиях сброс прогресса находится только внутри меню-гамбургера, чтобы исключить случайное нажатие. В этом же меню показываются сведения об игре и её версия.
- Нижняя постоянная инструкция отсутствует на всех разрешениях.
- Мобильные карточки элементов в рабочей области и панели выбора уменьшены примерно на 15%; размеры зон столкновения и ограничения перетаскивания должны соответствовать визуальному размеру карточек.
- Мобильная панель выбора должна вертикально прокручиваться свайпом из любой точки, включая карточки элементов. При выходе пальца из панели жест должен по-прежнему позволять перетащить выбранный элемент на поле.
- Панель подсказки располагается выше элементов и чёрной дыры, не выходит за границы экрана и переносит длинный текст на несколько строк.

## Версионирование

- Текущая версия хранится в единственной константе `APP_VERSION` в `src/game/app-meta.js` и выводится в меню программы.
- При каждом завершённом пользовательском обновлении игры обязательно повышать `APP_VERSION`, даже если GitHub пока не публикуется.
- Использовать семантический формат `MAJOR.MINOR.PATCH`: `PATCH` — исправление ошибки или небольшая правка, `MINOR` — новая функция, механика, элементы или заметное изменение интерфейса, `MAJOR` — несовместимое изменение сохранений или крупная переработка игры.
- В рамках одного пользовательского запроса повышать версию один раз после завершения всех входящих в него правок.
- Перед публикацией сверять, что номер версии в меню соответствует публикуемому `index.html`.

## Проверка изменений

- После любой правки в `src/` выполнить `node tools/build.mjs`, затем `node tools/validate-game-data.mjs` (проверяет собранный `index.html`).

- Перед публикацией проверять синтаксис встроенного JavaScript и отсутствие ошибок разметки.
- Не считать публикацию завершённой, пока адрес GitHub Pages не открывается и игра не загружается без ошибок.
